# Spring Boot 项目标准骨架：各层如何配合、如何串联

> 目标：看懂**一个真实项目是怎么组装的**，以及每个零件挂在哪、由谁调用。
> 全部以本项目（`D:\StackLab\Springdemo`）的实际代码和实际缺口为例，不讲空话。

---

## 一、先给结论：一个项目只有 4 类东西

不要把框架当知识背，记住这个分类就够了：

| 类别 | 是什么 | 本项目里的例子 |
|---|---|---|
| **① 入口层** | 接 HTTP 请求，管认证、参数、响应格式 | Controller、Interceptor、参数校验、全局异常处理、统一响应包装 |
| **② 业务层** | 管业务规则和事务边界 | Service |
| **③ 数据层** | 管「数据从哪来」 | Mapper、Entity、XML、连接池、数据库 |
| **④ 横切关注点** | 不属于某一层，但每层都要用 | 配置类、日志、缓存、工具类、异常定义 |

**任何 Spring Boot 项目，你都能用这 4 类拆开。** 看懂一个陌生项目的方法就是：
先找 Controller（有哪些功能），再看 Service（业务规则），最后看 Mapper（数据从哪来）。

## 三、一次请求的完整旅程（对照上图找位置）

以「新增一条收藏」为例，看**每个零件依次登场**：

```
POST /api/bookmarks
Header: token: 123456
Body:   {"title":"我的收藏","url":"https://example.com"}
   │
   │ ① Tomcat 解析 HTTP，交给 Spring
   ▼
② Filter（字符编码）
   │
   ▼
③ LoginInterceptor.preHandle()          ★你已有
   │   读 header 的 token → 没有就 401，后面全不执行
   ▼
④ 参数绑定：JSON → BookmarkDTO 对象
   │   @RequestBody 让 Jackson 反序列化
   ▼
⑤ @Valid 校验                            ★你缺
   │   如果 DTO 上写了 @NotBlank，这里会拦下空 title → 400
   │   没有这一步，非法数据会一路流到数据库
   ▼
⑥ BookmarkController
   │   方法体通常只有 2~3 行：调 service，返回结果
   ▼
⑦ BookmarkService（接口）→ BookmarkServiceImpl
   │   @Transactional 从这里开始 ★你缺
   │   业务规则在这里：比如"同一 url 不能重复收藏"
   │   需要多个 Mapper 配合的写操作，事务保证一起成功或一起回滚
   ▼
⑧ BookmarkMapper.insert(dto)
   │   MyBatis-Plus 根据实体注解生成 INSERT 语句
   ▼
⑨ HikariCP 连接池 → 数据库真正执行
   │
   ▼
⑩ 返回主键 id 回填到对象
   │
   ▼
⑪ Service 返回 → Controller
   │
   ▼
⑫ 统一响应包装                            ★你缺
   │   把结果包成 {code:200, message:"ok", data:{...}}
   ▼
⑬ Jackson 转 JSON → HTTP 201 返回

  ※ 任何一步抛异常，都会被 ⑭ 捕获：
⑭ @ControllerAdvice + @ExceptionHandler    ★你缺
      统一转成 {code:500, message:"..."}，而不是把 Java 堆栈暴露给前端
```

**关键认知**：`Controller → Service → Mapper` 是主干，但**一个能用的项目还需要
⑤⑦⑫⑭ 这 4 个空位**。你现在的项目是「主干完整、横切缺失」的状态。

这也解释了为什么你觉得"串不起来" —— 你看到的是一条**没有护栏的流水线**：
没有参数校验、没有统一异常、没有事务、没有统一响应格式。
真实项目里这 4 样是标配，它们恰好都挂在"主干之外"，所以最容易被忽略。

## 四、每个组件挂在哪、由谁调用、为什么需要

| 组件 | 挂在流水线位置 | 由谁触发 | 不写会怎样 |
|---|---|---|---|
| **Controller** | ⑥ | Spring 按 URL+方法匹配 | 无法接收请求 |
| **Interceptor** | ③ | Spring MVC，在 Controller **之前** | 任何人可调所有接口 |
| **@Valid** | ⑤ | Spring MVC 参数绑定阶段 | 非法数据入库，或每个方法里手写 if 判断 |
| **Service** | ⑦ | Controller 调用 | 业务逻辑堆在 Controller，无法复用/无法测试 |
| **@Transactional** | ⑦ | Spring AOP 代理 | 中途失败时数据只改了一半（脏数据） |
| **Mapper** | ⑧ | Service 调用 | 无法访问数据库 |
| **Entity** | ⑧↔⑨ | 被 Mapper 使用 | 无法把表映射成对象 |
| **DTO** | ⑤ | 接收请求体 | 用 Entity 接请求，前端能改不该改的字段（如 id） |
| **VO** | ⑫ | 返回响应 | 直接把 Entity 返回，会暴露表结构甚至敏感字段 |
| **统一响应包装** | ⑫ | Controller 返回值 | 每个接口返回格式都不一样，前端要写 N 套解析 |
| **@ControllerAdvice** | ⑭ | 任何一层抛异常 | 前端收到 Java 堆栈，且每个方法都要 try-catch |
| **配置类** | ④ | Spring 启动时 | 插件不生效（如分页静默失效） |
| **Swagger 注解** | 旁路 | 被 springdoc 读取 | 只是没文档，不影响运行 |

## 五、识别模式：这个骨架在真实项目里一模一样

这是最有价值的一点 —— **学会一个，看懂所有**。

| 层 | 本项目 | 若依 RuoYi | mall（电商） | 你的下一个项目 |
|---|---|---|---|---|
| Controller | `DbQueryController` | `SysUserController` | `OmsOrderController` | ? |
| Service | `SysUserService` | `ISysUserService` | `OmsOrderService` | ? |
| Mapper | `SysUserMapper` | `SysUserMapper` | `OmsOrderMapper` | ? |
| Entity | `SysUser` | `SysUser` | `OmsOrder` | ? |
| XML | `SysUserMapper.xml` | `SysUserMapper.xml` | `OmsOrderMapper.xml` | ? |
| 统一返回 | 无（该补） | `AjaxResult` | `CommonResult` | `Result<T>` |
| 全局异常 | 无（该补） | `GlobalExceptionHandler` | `GlobalExceptionHandler` | `GlobalExceptionHandler` |

**看懂这张表，你就掌握了 80% 的 Java Web 项目结构。**
名字不同、包名不同，但**分层和调用关系完全一致**。

> 所以读陌生项目的正确姿势：
> 1. 找 `*Controller` → 知道有哪些功能、URL 长什么样；
> 2. 挑一个接口，沿着 `Controller → Service → Mapper` 读下去 → 知道它是怎么实现的；
> 3. 找 `GlobalExceptionHandler` 和统一返回类 → 知道它的响应格式约定。
>
> 三步下来，一个陌生项目你就能上手改需求了。

## 六、功能是怎么"加"上去的：模块化思维

**核心认知：一张表 ≈ 一个模块 ≈ 一套 Controller/Service/Mapper。**

你的 `bookmark` 表要变成一个功能，就是复制这一套（**这就是那个练习在练的东西**）：

```
新需求：「加一个收藏夹功能」
   │
   ├─ 1. 建表              db/bookmark-schema.sql
   ├─ 2. 实体              entity/Bookmark.java
   ├─ 3. Mapper            mapper/BookmarkMapper.java        （单表不用 XML）
   ├─ 4. Service + Impl    service/BookmarkService(+Impl)    （写业务规则）
   ├─ 5. Controller        controller/BookmarkController     （定 URL）
   └─ 6. 文档注解          @Tag / @Operation                  （可选）
```

**横向扩展（加功能）**：重复上面 6 步，每张表一套。
**纵向增强（加能力）**：往流水线上插横切组件 —— 这就是你缺的 4 样。

两条线是正交的：加功能不改变骨架，加能力不改变功能。

## 七、你该补的顺序（按收益排序）

| 优先级 | 补什么 | 为什么排这个位置 | 收益 |
|---|---|---|---|
| **1** | `Result<T>` 统一响应 + `@ControllerAdvice` 全局异常 | **这是「一个项目成型」的标志**。有了它，所有接口格式统一，前端只需一套解析 | 骨架立刻完整，最有"项目感" |
| **2** | `@Valid` + DTO 参数校验 | 把校验从业务代码里剥离出来，Controller 变干净 | 消除大量 if-else |
| **3** | `@Transactional` 事务 | 多表写操作必须用，否则数据不一致 | 数据安全底线 |
| **4** | 日志（`@Slf4j` 或 `Logger`） | 替换掉示范代码里的 `System.out.println` | 生产必备 |
| 5 | 缓存、异步、定时任务 | 有性能需求时再说 | 暂时不用学 |

**注意 1 和 2 是一对**：统一响应包装负责"成功长什么样"，
全局异常处理负责"失败长什么样"。两个都在，接口契约才算完整。

## 八、实战：骨架补全前后的真实对比

以下是本项目实际的改造记录（`UserController` / `DbQueryController`），不是示意。

### 9.1 新增的骨架组件

| 文件 | 作用 | 对应流水线位置 |
|---|---|---|
| `common/Result.java` | 统一响应结构 `{code, message, data}` | ⑫ 响应包装 |
| `common/BizException.java` | 业务异常，区分"预期错误"与"代码 bug" | ⑦ 业务层抛出 |
| `common/GlobalExceptionHandler.java` | 全局异常出口，9 个处理器覆盖各类错误 | ⑭ 异常出口 |
| `dto/BookmarkRequest.java` | 请求体 DTO + 校验注解 | ⑤ 参数校验 |
| `controller/DemoController.java` | 故意出错的演示（异常 + 事务回滚） | 教学用 |
| `controller/ValidationDemoController.java` | `@Valid` 校验演示 | 教学用 |

### 9.2 Controller 代码变简单了（这是骨架的价值）

**改造前**（`UserController.getById`）：

```java
public ResponseEntity<?> getById(@PathVariable Long id) {
    User user = store.get(id);
    if (user == null) {
        return notFound(id);            // 手工拼 Map + 设状态码
    }
    return ResponseEntity.ok(user);      // 手工包一层
}

private ResponseEntity<Map<String, Object>> notFound(Long id) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(Map.of("message", "用户不存在: id=" + id));
}
```

**改造后**：

```java
public Result<User> getById(@PathVariable Long id) {
    User user = store.get(id);
    if (user == null) {
        throw BizException.notFound("用户不存在: id=" + id);   // 只管抛，格式由全局处理器保证
    }
    return Result.ok(user);
}
```

**少了一个私有方法，错误路径和成功路径都只有一行。**
这就是"横切关注点"的意义：把重复的格式处理从每个方法里挪出去，集中到一处。

### 9.3 响应格式的真实变化（curl 实测）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 查列表成功 | `[{...},{...}]` 裸数组 | `{"code":200,"message":"成功","data":[...]}` |
| 查不存在用户 | `{"message":"用户不存在: id=999"}` | `{"code":404,"message":"用户不存在: id=999","data":null}` |
| name 为空 | `{"message":"name 不能为空"}` | `{"code":400,"message":"name 不能为空","data":null}` |
| 不存在的路径 | Spring 默认 JSON（含 `trace` 堆栈） | `{"code":404,"message":"接口不存在: /api/nothing","data":null}` |
| 运行时异常 | 500 + Java 堆栈泄漏 | `{"code":500,"message":"服务器内部错误，请联系管理员","data":null}` |
| 分页 | `{"records":[...],"total":12,...}` | `{"code":200,"data":{"records":[...],"total":12,...}}` |
| 删除成功 | 204，无响应体 | `{"code":200,"message":"成功","data":null}` |

**注意三个取舍**（没有免费的午餐）：

1. **DELETE 从 204 变成了 200**：204 的语义是"成功且无响应体"，
   为了让所有接口格式统一，这里改为 200 + `data: null`。
   两种做法都合规，团队选一种并保持一致即可；
2. **分页的 `records/total` 多了一层 `data`**：前端取值从 `res.total` 变成 `res.data.total`；
3. **POST 新增从 201 变成 200**：同样是为了统一。如果要保留 201，
   可以返回 `ResponseEntity.status(201).body(Result.ok(user))`，但那样又打破了"格式统一"的初衷。

> 这就是"统一格式"必须付出的代价：**要么全部统一，要么全部不统一**。
> 半统一（有的接口包、有的不包）比不统一更糟 —— 前端要写两套解析。

### 9.4 事务回滚的真实证据（本项目实测）

调用 `/api/demo/tx/large-name`（带 `@Transactional`）：

```
调用前 sys_user total = 12
调用后 sys_user total = 12   ← 第一条插入被回滚
```

调用 `/api/demo/no-tx/large-name`（**同样的代码，只少了 `@Transactional`**）：

```
调用前 sys_user total = 12
调用后 sys_user total = 13   ← 多出一条"事务测试"，脏数据
```

**两张表放在一起看，`@Transactional` 的价值就不需要解释了。**

## 九、尚未统一的部分（诚实记录）

补全骨架是**渐进**的，以下接口**故意保持原样**，因为它们各自在演示别的知识点：

| 接口 | 保持原样的原因 |
|---|---|
| `/hello`、`/hello/form`、`/hello/json` | 演示「GET/POST 参数绑定」，返回值简单反而更清楚 |
| `/api/files/upload`、`/api/files/download/**` | 演示文件上传下载，返回 `ResponseEntity<Resource>`（要控制 Content-Type 和响应头，**不适合用 Result 包装**）；上传接口用 `ResponseEntity.badRequest()` 手工返回错误 |
| `/api/demo/**` | 教学演示，已用 Result |

**真实项目里要统一，需要逐个改造**。这里留着不动，是为了让你能对照
「包了的」和「没包的」两种风格，理解统一格式的收益和代价。

## 十、排错映射表（按图定位，这是骨架图最实用的地方）


| 现象 | 卡在第几环 | 去哪儿找 |
|---|---|---|
| 连不上 | ① Tomcat | 服务起了吗、端口对不对 |
| 401 | ③ Interceptor | token 头带了吗 |
| 400 + 字段校验失败 | ⑤ @Valid | DTO 上的校验注解 |
| 404 | ⑥ Controller 匹配 | URL 和 HTTP 方法对不对 |
| 415 | ④ 参数绑定 | `Content-Type` 头 |
| 500 + 堆栈 | ⑦⑧ 业务或数据 | 看日志最后一行的 `Caused by` |
| 前端说"格式不对" | ⑫ 统一响应 | 有没有包装类 |
| 数据改了一半 | ⑦ 事务 | `@Transactional` 加了吗、方法是不是 public |
| 返回里出现不该给的字段 | ⑫ VO | 是不是直接把 Entity 返回了 |
| SQL 没有 LIMIT | 配置类 | 分页插件注册了吗 |

## 十一、一句话总结

> **主干是 `Controller → Service → Mapper`，横切是「校验进、异常出、事务包中间、格式统一」。
> 功能靠复制这套骨架横向长出来，能力靠往流水线上插横切组件纵向长出来。**
